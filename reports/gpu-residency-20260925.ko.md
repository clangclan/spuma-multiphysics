# GPU 상주(residency) 실험 (2026-09-25)

기준은 [1스텝 시간 단축](step-time-optimization-20260925.ko.md)을 적용한 빌드(`stableGasPrune`, 2.325 s/스텝)다. 벤치마크는 모두 40 bar 160³ 사례의 200 μs 체크포인트에서 10스텝을 진행하고, 2–10스텝 평균을 냈다. 모든 실험에서 10스텝 뒤 `reactiveState.bin`을 기준 빌드와 비트 단위로 비교했다.

**2.325 s → 1.874 s(−19%)**다. main의 `stableGasPrune`(3.46 s) 대비 1.85배, `reference`(7.78 s) 대비 4.2배다. CPU fallback과 장치 실패는 모두 0이었다. A와 B는 검증 모드(`REACTIVE_WALE_STATES_CHECK=1`)로도 한 번씩 돌렸고, 결과가 같았다.

## 출발점: 전송이 어디서 생기는가

Nsight 2스텝(2.33 s/스텝 빌드)의 호스트↔GPU 전송을 NVTX 구간별로 나눴다.

| 구간 | 방향 | GB/스텝 | s/스텝 |
|---|---|---:|---:|
| WALE PR 상태 (`tr-wale-pr`) | H2D | 3.15 | 0.140 |
| HEM 입력 | H2D | 1.94 | 0.087 |
| HEM 출력 | D2H | 1.47 | 0.101 |
| 수송 상태 (`tr-validate-upload-state`) | H2D | 0.92 | 0.040 |
| 계면 기하 | D2H / H2D | 0.59 / 0.30 | 0.041 |
| 보존량 pack/unpack (pinned) | H2D / D2H | 0.59 / 0.59 | 0.043 |

같은 상태가 한 스텝에 여러 번 올라간다. 스텝 시작 CFL과 RK0이 같은 상태 S0을 쓰고, RK1 복원 뒤의 CFL과 RK1이 같은 상태 S1을 쓴다.

## A. WALE PR 상태 업로드 재사용

- **상태 epoch.** 솔버(`ReactiveFoam.C`)가 상태를 바꾸는 모든 지점에서 epoch를 올린다. 대상은 `recover()`(진입과 종료, 예외 포함), `react()`, RK2 seed 복원, 재시도·실패 복원 두 곳, 초기화, 체크포인트 로드다.
- **재사용 조건.** `packTransport`는 마지막 업로드 이후 epoch가 그대로일 때만 `reactive_transport_wale_pr_properties_v2(..., statesUnchanged=1)`을 부른다. 수송 라이브러리는 이때 장치 사본을 다시 쓴다. 장치 사본은 이 함수만 쓰고, 실패한 호출은 사본을 무효로 만든다.
- **복사 제거.** 비기계 상태는 연속 `ReactiveThermoState` 배열이므로, 호스트 `walePrStates` 복사(720 MB) 없이 포인터를 그대로 넘긴다.
- **enthalpy 복사 병렬화.** WALE enthalpy용 q 복사도 병렬화했다.
- **검증 모드.** `REACTIVE_WALE_STATES_CHECK=1`이면 재사용할 때마다 호스트 shadow와 memcmp하고, 다르면 중단한다.
- **효과:** 10스텝 WALE 업로드가 32.9 → 17.8 GB, 스텝이 2.325 → 2.155 s.

## B. 수송 상태 업로드·계면 기하 중복 제거 (`reactiveTransport.cpp`)

- **수송 상태 (56 B/셀).** 직전 업로드와 바이트가 같으면 검증과 업로드를 모두 건너뛴다. 병렬 memcmp로 비교하고, 장치 `v.state`는 `uploadState`만 쓴다. 실제로 올릴 때는 4.1M 셀 검증과 기체 셀 수 세기를 병렬로 한다.
- **계면 기하 (`diffuse` 모드).** 출력은 셀·고정 색의 순수 함수이고, 장치 색·곡률·표면에너지 배열은 `capillaryGeometry`만 쓴다. 입력 색이 직전과 바이트까지 같으면 GPU 작업과 전송 없이 직전 출력을 돌려준다. WALE 물성은 매 요청에서 무효화한다. `geometryBuilds`는 실제 GPU 기하 계산 횟수이므로 동일한 색을 재사용하면 증가하지 않는다. 따라서 동일 기하 epoch로 물성을 다시 계산할 수 있지만, 색이 바뀌어 기하를 재계산한 뒤에는 이전 epoch를 거부한다. 상태를 가진 `cartesianImplicit` 모드는 제외했다.
- **입력 검증.** 색 검증도 병렬화했다.
- **효과:** 10스텝 기하 빌드 93 → 51, 상태 업로드 9.63 → 4.82 GB, 스텝 2.155 → 2.094 s.

## C. HEM 직접 경로 (`closureHemPath direct`, 기본값 `pool`)

**문제.** 풀은 정확 재사용 hash, 입력 적재, gather/scatter, 재사용 반영, 출력 복사를 호스트에서 한다. 흐름이 발달한 지금은 정확 재사용 비율이 약 3%라 이 경로가 대부분 순수 오버헤드다. 정확 재사용을 끄기만 해도 결과는 비트 동일이었다(2.094 → 2.071 s). 결정적 계산이라 중복 셀을 직접 계산해도 같은 비트가 나온다.

**변경.**

- 솔버가 풀과 같은 라이브러리(`closureLibrary`)와 같은 모델 이미지(`reactive_rt_export_gpu_hem_v1`)로 자기 HEM 장치를 만든다.
- 모세관 UV 배치는 이미 pack한 배열(`batchQ`, `batchEnergy`, 색·압력차, seed)을 `reactive_gpu_hem_run_v2`에 바로 넘긴다.
- **실패 계약 유지:** 셀 하나라도 실패하면 seed를 다시 pack해서 같은 배치를 기존 풀로 재실행한다. 기존 풀의 실패 기록을 얻고 원래 시도는 반드시 롤백한다. 진단용 풀 재실행이 우연히 성공해도 원래 실패를 무시하지 않는다. 실제 실행된 두 GPU 호출의 시간·전송·실패 카운터를 모두 기록한다(검토에서 수정).
- **보고 카운터:** 성공·실패한 직접 배치의 HEM 카운터를 풀 카운터에 더해 `REACTIVE_GPU_HEM`과 `REACTIVE_GPU_HEM_STEP`에 보고한다. 검증기의 규칙은 그대로 적용된다. 두 핸들의 host/device 메모리도 합산하며, 실패한 배치의 비용을 숨기지 않는다.
- **허용 조건:** 모세관, strict CUDA HEM, CPU fallback 금지일 때만 허용한다.

**효과:** 복원이 1.329 → 1.109 s, 스텝이 2.094 → 1.874 s. HEM 호출 시간이 HEM wall과 같아졌다(0.725 vs 0.721 s). 풀 오버헤드가 없어졌다는 뜻이다.

## 남은 상주 작업 (구현하지 않음)

1.87 s/스텝에서 남은 호스트↔GPU 왕복의 뿌리는 **상태가 호스트에 있어야 하는 구조**다.

- HEM 출력(D2H 1.47 GB/스텝)을 호스트가 받아야 하는 이유: 액체 색 계산, 모세관 잔차, dirty 판정, 결과 반영, 수송 상태 compact, CFL primitive가 모두 호스트 루프이기 때문이다.
- 이 루프들을 장치로 옮기면 없어지는 것:
  - HEM 출력 D2H 약 0.10 s
  - WALE·수송 상태 업로드 나머지 약 0.1 s
  - pack·색·잔차·반영 호스트 시간 약 0.2–0.3 s
  - HEM 입력 H2D의 seed·q 몫 약 0.08 s
- 추정 절감은 합계 0.4–0.6 s/스텝이다(**측정값 아님**).
- 필요한 일:
  - 장치 상태 배열(4.1M × 176 B)을 수송 핸들이 소유하고, HEM이 그 배열을 직접 읽고 쓰게 한다. 수송과 HEM이 같은 `libreactiveTransport.so`라 같은 CUDA context를 쓴다.
  - 모세관 외부 반복을 장치 커널(색·잔차 reduction·dirty 압축)로 옮긴다.
  - 호스트 상태는 체크포인트·진단·실패 경로에서만 내려받는다.
- 주의할 점: 호스트 `internalEnergy`는 nvc++ `-O3`로 컴파일되어 FMA 축약이 들어갈 수 있다. 장치에서 다시 계산하면 비트가 달라질 수 있으므로, 비트 동일성을 유지하려면 에너지 계산은 호스트에 두거나 양쪽 연산 순서를 고정해야 한다.

추가로 결과 불변 후보가 둘 있다.

- HEM 직접 경로의 배치 파이프라인: 배치 k+1의 pack을 배치 k의 커널과 겹친다.
- 직접 경로 버퍼의 pinned 등록.

## main 반영 전 검토

- 저장된 9개 10스텝 실행의 최종 체크포인트를 직접 해시 비교했다. 모두 `4ddff82afbf2c83be1fb86d208f39582b6cb5330ff0bad9f01980e28a4a630ca`로 같았다. 독립 집계 평균은 기준 2.325394 → 직접 경로 1.874445 s/스텝이다.
- 보고된 19%는 이번 상주 실험의 추가 개선이며, main 대비 약 46% 단축에는 선행 백업·호스트 병렬화·전 기체 Newton 조기 종료까지 포함된다. FP32/INT 또는 허용오차 완화는 채택하지 않았다.
- 수송 상태 cache에 null 입력이 들어오면 비교 전에 오류로 거부하도록 수정했다. WALE v2의 실패 요청은 검증 단계에서 거부되더라도 재사용 가능 사본과 물성 게시 상태를 무효화한다.
- 직접 경로의 옵션 검증을 풀 생성 조건 밖으로 옮겨 지원되지 않는 설정을 조용히 무시하지 않도록 했다. 전 기체 Newton의 마지막 작은 보폭에서 이미 허용오차를 만족한 후보는 조기 종료로 버리지 않는다.
- 기존 WALE v1 검사는 같은 색의 반복 요청도 기하 버전을 증가시킨다고 가정해 실패했다. 동일한 색의 재사용과 변경된 색의 이전 epoch 거부를 구분하도록 확장했다. v1/v2 각각 73개 검사와 곡면 flash 회귀 검증을 통과했다.
- 완전한 GPU 상주는 아니다. direct 모드에서도 풀 핸들을 진단용으로 유지하고 별도 HEM 핸들을 할당하며, 수송/기하 host shadow도 추가로 보유하므로 메모리와 전송의 절충이 있다.
- 실제 160³ 솔버를 200 → 200.15 μs까지 pool/direct/검증 모드로 각각 실행한 결과가 main의 검토 결과와도 같은 `29b7c026…f3`이다. GPU 셀 실패를 강제로 한 번 넣은 pool/direct 실행은 모두 1회 롤백 후 4스텝으로 끝났으며 최종 상태도 서로 비트 동일했다. 직접 호출만 실패하고 진단용 풀 재실행은 성공하는 경우에도 원래 실패가 보존됨을 검증했다. CPU fallback은 모든 실행에서 0이다.
- 최종 GPU 라이브러리로 125/150/170/200 μs 3,693,404셀을 reference/stableGasPrune 각각 다시 재생했으며, 기존 main의 기준 탐색 결과와 모두 바이트 동일했다.
- 최종 솔버의 CUDA 호출 오류 주입에서도 pool/direct가 각각 한 번 재시도하고 같은 상태로 끝났다. 오류 문자열을 호출 완료 후 읽도록 수정해 메시지 누락도 방지했다. GPU 셀 수렴 실패와 API 실행 오류는 구분하며, API 오류는 셀 실패 카운터가 아닌 재시도 기록으로 검증했다. 최종 검토 요약은 `results/gpu-residency-20260925/main-review-summary.json`, 회귀 실행 도구는 `tools/validate_gpu_residency.py`다.
