## FP64 지수부를 얼마나 사용하는가

FP64는 부호 1비트, 지수 11비트, 저장 가수 52비트이며 정상수의 유효 정밀도는 숨은 1을 포함해 53비트다. 지수부가 매번 11비트를 차지하는 것과, 데이터가 전체 지수 범위를 사용하는 것은 다르다.

첫 압력·온도 행렬의 실제 FP64 값에서 `floor(log2(abs(v)))`를 조사했다. 0과 비유한 값은 별도로 세었다. 각 행렬은 **3,094,455행, 21,419,851개 계수**, 행당 최대 19개다.

| 계 | 해 x | 계수 A | 우변 b | Aij·xj | 기존 FP64 잔차 |
|---|---:|---:|---:|---:|---:|
| 압력 | 20…21 | -51…-23 | -69…-2 | -29…-2 | -81…-40 |
| 온도 | 8…8 | -31…3 | -7…11 | -23…11 | -72…-40 |

온도 자체는 모두 256–512 K 범위지만 작은 계수와 수렴 잔차에는 다른 스케일이 필요하다. 이 두 스냅샷의 관측된 지수는 합쳐서 −81…21 안에 있지만, 이것이 전체 솔버의 모든 중간값·시간에서의 범위 보장은 아니다. 지수 범위가 좁아도 서로 비슷한 값을 뺄 때 필요한 가수 정밀도는 남는다. [전체 분포·스냅샷 해시](integer-exponents.json)

## INT32, FP32 혼합, 2INT32의 실제 비교

각 행의 A 최대값에 공통 지수 eA를 두고, x에는 전역 공통 지수 eX를 둔다. `a≈qA·2^(eA−F)`, `x≈qX·2^(eX−F)`로 변환했다. INT32는 F=30과 INT64 누적, 2INT32는 F=62와 128비트 누적을 사용한다. 후자의 입력은 8바이트이고 누산기는 16바이트다. b도 곱의 스케일로 반올림해 잔차를 정수로 누적한다.

`|b_q|+Σ|qA·qX|`를 넓은 정수로 미리 검사하며, capacity를 넘으면 누적 전에 실패한다. 각 GPU 정수 누적값과 마지막 FP64 반올림을 **모든 행에서 독립 CPU __int128 계산과 대조해 불일치 0건**을 확인했다. 원래 FP64 입력에 대한 정확도는 결정적으로 선택한 32,768행에서 113비트 계산과 비교했다. 원래 입력의 양자화 오차까지 0이라는 뜻은 아니다.

최종 F30/F62 구현의 CUDA event 중앙값, 단위 ms:

| 방식 | 압력 Ax | 압력 잔차 | 온도 Ax | 온도 잔차 |
|---|---:|---:|---:|---:|
| FP64 | 0.3465 | 0.3723 | 0.3467 | 0.3732 |
| FP32 | 0.2287 | 0.2427 | 0.2283 | 0.2424 |
| 2FP32 (DS) | 0.3416 | 0.3697 | 0.3562 | 0.3700 |
| INT32 + INT64 누적 | 0.2466 | 0.3021 | 0.2461 | 0.3024 |
| 2INT32 + 128비트 누적 | 0.3619 | 0.4186 | 0.3621 | 0.4181 |

INT32 저장값을 FP32로 변환해 FMA하는 hybrid도 측정했다. 압력/온도 Ax는 각각 0.2470/0.2467 ms였다. 이 경로의 산술 정밀도는 FP32다.

INT32 잔차의 최대 행 스케일 대비 오차는 압력 3.15e−9, 온도 2.69e−9였고, 2INT32는 각각 6.14e−19, 4.28e−19였다. 매우 작은 수렴 잔차를 분모로 하는 상대 오차는 훨씬 커질 수 있다. 예를 들어 INT32 압력 잔차의 상대 L2 오차는 약 7.23e3이다. 정수 내부 반복의 수렴이나 전체 CFD 정확도를 검증한 결과는 아니다. 입력의 비영 계수·x가 0으로 바뀐 수는 두 방식 모두 0이었다.

측정은 5개 round이며, packing은 round당 3회, Ax/잔차는 20회 반복했다. 행별 지수 검색은 packing에 포함한다. CPU 전역 x 지수 검색, 전송·할당·CPU 검증은 제외한다. 정수 출력은 FP64, FP 경로 출력은 native 형식이므로 저장량도 다르다. 압력은 FP 비교 뒤 정수, 온도는 정수 뒤 FP 비교 순서다. 실제 solver에서는 스케일 유지·재설정 비용이 추가된다. [압력 원자료](integer-pressure-v4.json), [온도 원자료](integer-temperature-v4.json), [현재 SASS](integer-sass.json)

RTX Blackwell은 FP32와 INT32 코어를 통합해 같은 클록에 둘 중 하나로 동작한다. 따라서 INT32가 별도로 놀고 있는 FMA 자원을 제공하지는 않는다. 공식 처리량 표에서도 sm_120의 FP32 FMA는 SM·클록당 128 결과, INT32 곱/MAD는 64, 확장 정수 MAD는 32로 제시된다. 64×64→128 곱·carry·스케일 복원은 여러 명령이 필요하다. [NVIDIA 아키텍처 백서](https://images.nvidia.com/aem-dam/Solutions/geforce/blackwell/nvidia-rtx-blackwell-gpu-architecture.pdf), [CUDA native 처리량 표](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#throughput-of-native-arithmetic-instructions)

배열을 각각 한 번 읽고 결과를 한 번 쓴다고 환산한 압력 Ax 유효 대역폭은 FP64 약 920 GB/s, FP32 약 912 GB/s다. 공식 메모리 최고치는 960 GB/s다. **희소 연산의 데이터 이동 비용이 크다는 근거지만, 실제 DRAM 카운터 측정은 아니다.** 캐시 재사용과 접근 효율은 이 환산에 반영하지 않았다. 연산 형식만 바꿔 최고 산술 처리량 비율만큼 빨라지기 어려운 이유다. [배열 크기 산식](integer-gpu-exploration.json), [RTX 5080 메모리 사양](https://images.nvidia.com/aem-dam/Solutions/geforce/blackwell/nvidia-rtx-blackwell-gpu-architecture.pdf)

## 낮은 전력과 높은 사용률의 원인, 적용한 변경

`nvidia-smi`의 GPU 사용률은 표본 시간 중 하나 이상의 커널이 실행된 시간 비율이다. 모든 연산 코어가 얼마나 많은 유효 명령을 수행했는지를 뜻하지 않는다. 이번 장치 전체 관측에서는 사용률 약 90%, 전력 약 150–160 W, 한도 360 W였으며 관측 표본의 전력·열 제한 플래그는 비활성이었다. SM/warp 점유율용 하드웨어 카운터는 현재 권한 제한으로 사용하지 못했다. [NVIDIA 사용률 정의](https://docs.nvidia.com/deploy/nvml-api/structnvmlUtilization__t.html)

선택형 `pintleAsyncGaussSeidel`을 구현했다. 같은 색상·행 산술·FP64 정밀도를 유지하면서 색상 커널을 같은 default stream에 enqueue한다. 단일 프로세스, 활성 interface 없음, pooled source, source와 psi가 다른 경우에는 우변 복사 없이 모든 sweep 뒤 한 번 완료를 기다린다. 다른 경우에는 기존 복사·interface 처리와 sweep별 fence를 유지한다. 설치된 SPUMA 공용 executor는 수정하지 않았다.

최종 구현과 새 기준 실행을 각각 20초 준비 후 10초 추적했다. 다음은 **추적한 프로세스의 GPU 활동**이며, 서로 다른 10초 구간에는 처리된 작업량도 다를 수 있다.

| 프로파일 지표 | 기준 | 개선 |
|---|---:|---:|
| 색상 커널 뒤 평균 공백 | 10.028 μs | 1.806 μs |
| GPU 활동 시간의 합집합 / 구간 길이 | 60.47% | 64.49% |
| 색상 커널 수 | 69,569 | 77,320 |

평균 공백은 약 82% 감소했다. GPU 활동 비율 증가는 ALU 점유율 증가량과 같지 않다. host 동기화 대기는 GPU 계산과 겹치므로 두 시간을 합산해 예상 절감량으로 삼을 수 없다. [새 추적 집계](async-current-traces.json), [기존 추적 집계](async-original-trace.json)

## 전체 CFD 검증

45.00→45.36 μs, dt=30 ns, 12스텝씩 **4쌍, 총 8회** 실행했다. 각 run의 첫 2스텝과 마지막 저장 스텝을 제외한 9스텝 평균을 구했다. B→A, A→B를 반복해 양쪽 선행 횟수를 같게 했다. 최종 캠페인 중 추가 빌드나 정수 벤치마크를 병행하지 않았다. 데스크톱 프로세스까지 격리한 전용 GPU 실험은 아니다.

| 설정 | 초/스텝 중앙값 | run별 범위 | 장치 전체 평균전력의 중앙값 |
|---|---:|---:|---:|
| 기준 FP64 | 2.092435 | 2.076242–2.098744 | 154.77 W |
| 선택형 비동기 FP64 | 2.011949 | 1.993566–2.015000 | 157.98 W |

중앙값끼리 비교한 시간 감소는 3.85%, 같은 repeat끼리 비교한 감소율의 중앙값은 **3.79%**다. 네 쌍 모두 개선됐으며 각각 3.06%, 4.14%, 5.01%, 3.45% 줄었다. 압력 단계 중앙값은 0.788→0.698초로 약 11.4% 줄었고, 다른 단계는 거의 그대로였다. 전력 수치는 장치 전체 표본이므로 solver만의 에너지로 해석하지 않는다.

앞선 ‘색상별 sync만 제거’ 캠페인은 기준 시간이 2.127→1.946→1.827초로 흔들렸고 개선을 재현하지 못했다. 해당 결과를 이번 최종 캠페인과 합치지 않았다. 최종 수치가 이 추가 구현과 측정 조건에서의 결과라는 점을 유지한다.

각 run의 선형 solve 192회, 총 반복 수 384회였고, 네 쌍의 필드별 반복 횟수 순서는 모두 일치했다. 주요 상태 필드의 최대 scaled 차이는 p 4.21e−10, T 1.87e−10, rho 5.54e−10, U 7.40e−10 이하, alpha는 1.99e−8 이하였다. 모든 필드는 유한했고 p/T/rho는 양수였다. phase sum 오차는 2.88e−13 이하, 단계별 질량 불균형 진단은 5.06e−8 이하였다.

이는 MAIN의 기존 개발용 screen(p 1e−5, 나머지 상태 1e−6, alpha sum 1e−9, 질량 진단 1e−6)을 통과한 것이다. **raw dgdt는 같은 상대 정밀도로 일치하지 않았다**: 최대 scaled 차이는 air 1.0, IPA 약 0.8545, N2O 약 0.00659다. 첫 쌍의 동시 최종 상태로 재구성한 `S_i=alpha_i·(Σ alpha_j·dgdt_j−dgdt_i)`에서 `max|dt·ΔS_i|`는 1.96e−12 이하였다. 이는 순차 alpha transport 재현이나 장시간 물리 검증을 대신하지 않는다.

실제 mesh 1스텝의 `pintleAsync` 커널 메모리 검사와 명시적 CUDA API 검사는 오류 0건이었다. 이후 host-only source를 기존 경로로 보내는 `usePool` guard를 추가했다. 최종 라이브러리와 검사한 라이브러리의 colorLoop device SASS가 동일함을 확인했고, 최종 라이브러리를 위 전체 캠페인에서 실행했다. 전체 SPUMA race 검사 통과를 뜻하지 않는다. [커널 동등성·바이너리 해시](async-memcheck-kernel-equivalence.json)

원본 초기장·mesh·상수 36개 파일은 8개 복사 case 및 보존된 원본 해시와 대조했다. 변경된 thermo dictionary는 run별 설정 해시와 비교했다. 바이너리, controlDict, fvSolution은 캠페인 전후 동일했고 최종 소스 해시도 보존한다. [입력 무결성](async-input-integrity.json), [수치·시간·해시 집계](integer-gpu-exploration.json)

## 남은 적용 범위

기본 FP64 경로는 유지하며, 새 smoother는 설정으로 선택한다. 정수 커널은 별도 연구 도구다. 추가 후보는 reduction의 과도한 dynamic shared-memory 예약(관측값 91,238 B), 불필요한 scalar 초기화, 유한체적 atomic scatter를 cell gather로 합치는 작업이다. 이들은 현재 변경에 포함하지 않았고, 특히 reduction·합산 순서 변경에는 별도 검증이 필요하다.

비공개 GitHub에는 소스·도구·보고서를 올린다. 대용량 case, CSR 스냅샷, 바이너리, Nsight 원자료는 `.gitignore` 대상으로 로컬에 보존한다. 최초 업로드는 로컬 커밋 이력 전체 대신 동일 파일·실행권한의 새 스냅샷 커밋을 만든 방식이다.
