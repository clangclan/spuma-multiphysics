# FP32·2FP32·3FP32 대체 실험

**FP32 내부 반복과 FP64 잔차보정은 실제 Pintle 온도 방정식에서 성립했다. 전체 시간의 추가 이득은 작았다.** 2FP32는 계산 위주 시험에서 빨랐지만 실제 희소행렬에서는 FP64와 대체로 동급이었다. 3FP32는 더 높은 정밀도를 냈으나 계산 비용과 저장량이 커서 이번 속도 최적화에는 적합하지 않았다. 실험 모듈을 별도 옵션으로 남기고 기존 FP64 기본값을 유지한다.

[재현·구현 안내](../README.precision.ko.md) · [집계 JSON](precision-exploration.json) · [전체 CFD 원자료](../benchmarks/precision-temperature-full12/benchmark.json)

## 서로 다른 세 수준의 성능

RTX 5080(sm_120), Ryzen 5 9600X, 드라이버 595.91.07, CUDA 13.2 / HPC SDK 26.5 환경이다. NVIDIA의 RTX Blackwell 문서는 FP64 peak 처리량을 FP32의 1/64로 명시한다. 이것은 하드웨어 산술 처리량이며 애플리케이션의 가속 상한을 그대로 뜻하지 않는다. [NVIDIA 아키텍처 문서](https://images.nvidia.com/aem-dam/Solutions/geforce/blackwell/nvidia-rtx-blackwell-gpu-architecture.pdf)

아래는 실제 압력 행렬 3,094,455행·21,419,851개 비영 계수를 standalone CSR 커널로 계산한 결과다. 행렬·벡터 변환 시간은 별도로 측정했다. CUDA event 5라운드의 중앙값이며 CSR은 라운드마다 20회 실행했다. 계산 시험은 262,144개 thread에서 4개의 독립적인 512회 recurrence를 수행한다. DS/TS의 논리적 multiply-add 하나에는 여러 FP32 명령이 필요하므로 이 연산 수를 하드웨어 FLOP 수로 세지 않는다.

| 형식 | 한 수의 저장량 | 계산 recurrence ms | FP64 대비 계산 속도 | CSR Ax ms | FP64 대비 Ax 속도 | 입력 변환 ms |
|---|---:|---:|---:|---:|---:|---:|
| FP64 | 8 B | 1.72799 | 1.00× | 0.42880 | 1.00× | 0.62939 |
| FP32 | 4 B | 0.03905 | 44.25× | 0.29196 | 1.47× | 0.38630 |
| 2FP32 / DS | 8 B | 0.59374 | 2.91× | 0.40332 | 1.06× | 0.54966 |
| 3FP32 / TS | 12 B | 6.05722 | 0.285× | 0.60692 | 0.707× | 0.75633 |

FP64와 DS의 Ax 라운드 범위는 각각 0.3991–0.4340 ms, 0.3900–0.4391 ms로 겹친다. DS의 6% 중앙값 차이를 확정적인 가속으로 보지 않는다. 희소행렬은 값뿐 아니라 index·벡터 접근 비용도 부담한다. DS는 FP64와 같은 8 B이고 TS는 12 B여서 FP32처럼 저장 폭을 줄이지 못한다. 위 값은 원래 SPUMA 압력 솔버의 전체 시간이나 GAMG의 속도가 아니다.

TS에서 동적 local-array 접근을 제거한 뒤 이 표를 측정했다. 최종 recurrence/CSR 커널의 ptxas 보고는 stack·spill 0 B다. 따라서 여기에 기록한 TS의 느림을 이미 제거한 local-memory 문제로 설명하지 않는다. [빌드 로그](../logs/build-precision-lab.log) · [행렬 시험 원자료](../benchmarks/precision-pressure-snapshot1/precision-lab-v2.json)

## 정밀도는 FP64와 교환 가능한가

DS는 `hi+lo`, TS는 `hi+mid+lo`를 계산하는 커스텀 산술이다. 단순히 CUDA `float2/float3`에 값을 담은 것과 다르다. DS의 유효 정밀도는 대략 45–48비트로 FP64의 53비트에 못 미친다. 둘 다 FP32의 지수 범위를 확장하지 않는다. [NVIDIA float-float 설명](https://docs.nvidia.com/cuda/cuest/0.2.0/scalar_emulation.html)

TS는 [Fabiano–Muller–Picot의 triple-word 산술](https://perso.ens-lyon.fr/jean-michel.muller/08721180.pdf)의 Algorithms 4/5/8/9를 구현했다. RN, 정규화된 입력, 중간 underflow/overflow 없음이라는 조건이 필요하다. 현재 구현은 덧셈·뺄셈·곱셈이며 FP64 나눗셈·제곱근·EOS 초월함수의 전체 대체품은 아니다.

32,768개 scalar 입력쌍을 113비트 기준으로 검사했다. 이 집합은 작은 차이가 남는 상쇄 사례를 의도적으로 많이 포함한다. 아래 비율을 실제 CFD 셀에서의 실패 확률로 해석하면 안 된다.

| 형식 | 변환된 입력 기준 최대 덧셈 상대오차 | 최대 곱셈 상대오차 | 원래 비영 합이 입력 변환 중 0이 된 사례 |
|---|---:|---:|---:|
| FP64 | 1.10e−16 | 1.11e−16 | 0 |
| FP32 | 5.94e−8 | 5.90e−8 | 24,557 |
| DS | 5.14e−15 | 1.29e−14 | 6,672 |
| TS | 1.35e−22 | 7.55e−22 | 0 |

DS/TS의 각 성분을 직접 113비트로 변환해 더했다. 낮은 성분을 먼저 FP64나 host `long double`로 합쳐 잃지 않도록 했다. 정규화 검사와 모드별 산술 screen은 모두 통과했지만, 이것은 모든 입력의 올바른 반올림이나 FP64 동등성의 증명이 아니다.

실제 수렴한 압력 시스템에서 32,768행을 일정 간격으로 골라 `b−Ax`를 비교한 결과는 다음과 같다. 전체 행의 약 1.06% 표본이며 전체 행렬의 최댓값이라고 주장하지 않는다.

| 형식 | 잔차의 최대 절대오차 | 최대 오차 / 행 크기¹ | 잔차 상대 L2 오차 |
|---|---:|---:|---:|
| FP64 | 8.86e−21 | 1.39e−16 | 5.48e−8 |
| FP32 | 2.98e−8 | 1.11e−7 | 2.32e5 |
| DS | 2.08e−15 | 7.15e−15 | 9.81e−3 |
| TS | 4.57e−23 | 2.66e−22 | 1.95e−10 |

¹ 행 크기는 `|b_i|+Σ_j|a_ij*x_j|`다. 상대 L2의 분모는 이미 매우 작은 수렴 잔차다. 큰 상대값을 압력장 자체의 상대오차로 해석하지 않는다. 이 실험은 압력 잔차 계산을 FP32로 직접 바꾸기 어렵다는 근거이며, FP32 전처리와 FP64 외부 반복의 가능성을 배제하지 않는다.

범위 확인용 `1e−60`은 FP32/DS/TS 모두 0이 됐다. 현재 압력 행렬에는 이 underflow 한계에 걸리는 입력이 없었다. 따라서 이 행렬에서의 통과가 큰 동적 범위에 대한 검증은 아니다. `--ftz=false`와 명시적 RN을 사용했고 `fast-math`는 사용하지 않았다.

## 실제 온도 방정식에 적용

첫 온도 행렬에서 `Σ|offdiag|/diag`의 최대값은 약 0.1175로 대각 우세였다. [행렬 집계·snapshot hash](precision-temperature-matrix.json)에 계산식을 기록했다. 이를 바탕으로 내부 Jacobi를 낮은 정밀도로 수행하고, FP64로 실제 잔차를 계산해 보정하는 실험을 작성했다. 원래 온도 증분과 같은 L1 정규화·허용오차 `1e−12`를 사용했다.

모든 경우 GPU limiter·GPU 물성·압력·운동량 설정은 같고 온도 선형해법만 다르다. `baseline`은 기존 FP64 multicolor 증분 해법, `IR-FP64`는 새 Jacobi·잔차보정 알고리즘의 FP64 대조군이다. FP32 자체의 효과는 IR-FP64와 비교해야 한다.

45.00→45.36 μs, dt=30 ns, 12스텝×3회×5설정을 실행했다. 첫 2스텝과 마지막 출력 스텝을 제외한 9스텝 평균의 실행별 중앙값이다. 아래 에너지 단계에는 온도 풀이 이외의 에너지·물성 작업도 포함된다.

| 설정 | 전체 s/step 중앙값 | 실행별 범위 | 에너지 단계 s/step | 기존 baseline 대비 전체 속도 |
|---|---:|---:|---:|---:|
| baseline FP64 | 2.07212 | 2.03826–2.20683 | 0.16880 | 1.000× |
| IR-FP64 | 2.03537 | 2.00982–2.12777 | 0.13338 | 1.018× |
| IR-FP32 | 1.99817 | 1.99181–2.01380 | 0.12640 | 1.037× |
| IR-DS | 2.00559 | 2.00419–2.01040 | 0.13146 | 1.033× |
| IR-TS | 2.01238 | 2.01225–2.03840 | 0.13745 | 1.030× |

**IR-FP32의 기존 baseline 대비 시간 감소는 3.57%지만, 전부 FP32 덕분은 아니다.** 새 해법의 FP64 버전에서도 개선이 있었다. IR-FP32와 IR-FP64의 중앙값 비율은 1.0186×이며 같은 반복끼리 나눈 비율의 중앙값은 1.0107×다. 반복 범위가 겹치고 3회 표본이므로 안정적인 전체 가속을 확정하지 않는다. 에너지 단계의 같은 반복 대비 배율은 1.0552×로, 그 단계의 약 5.2% 시간 감소를 관측했다.

IR-DS의 같은 반복 대비 전체 배율은 1.0124×, IR-TS는 0.9987×였다. 에너지 단계는 각각 1.0164×, 0.9624×였다. TS가 전체 중앙값 표에서 조금 빨라 보인다는 이유로 FP64보다 유리하다고 결론 내리지 않는다.

실행 순서는 반복마다 한 칸 회전했다. 5개 설정에 3회 반복이므로 완전히 균형 잡힌 순서는 아니다. 과거 별도 배치의 1.8629 s/step과 이 배치의 수치를 직접 나눠 새 가속률로 계산하지 않는다. [같은 반복의 비율·단계별 수치](precision-exploration.json)

[컴파일된 inner Jacobi의 SASS 확인](precision-sass.json)에서 FP32/DS/TS 버전에 FP64 산술 명령은 없었다. 대각 역수 준비, 변환 일부, 보정 누적, 실제 잔차 계산은 의도적으로 FP64다. 이 확인은 전체 애플리케이션의 동적 FP64 비율 측정이 아니다. NCU 하드웨어 counter는 현재 계정에서 `ERR_NVGPUCTRPERM`으로 접근할 수 없어 CUDA event와 SASS·기존 Nsight Systems trace를 사용했다.

## 수렴과 상태 검사

IR 4설정의 288회 온도 solve는 모두 보정 2회×내부 6 sweep으로 수렴했고 fallback=0, invalidPacked=0이었다. FP32의 가장 큰 최종 정규화 잔차는 4.365e−15였다. 다른 IR 모드는 3.241e−16 이하였다.

아래는 각 모드와 같은 반복의 기존 baseline을 비교한 12스텝 최종장 차이의 최댓값이다. `max_scaled=max|candidate−reference|/max(1,max|reference|)`다.

| 필드 | IR-FP64 | IR-FP32 | IR-DS | IR-TS |
|---|---:|---:|---:|---:|
| p | 4.10e−10 | 5.49e−10 | 4.52e−10 | 5.70e−10 |
| U | 6.96e−10 | 6.53e−10 | 3.70e−10 | 6.91e−10 |
| T | 1.69e−10 | 1.56e−10 | 7.07e−11 | 1.74e−10 |
| rho | 5.67e−10 | 5.52e−10 | 5.11e−10 | 5.76e−10 |
| alpha.ipa | 4.52e−10 | 3.84e−10 | 4.32e−10 | 4.82e−10 |
| alpha.n2o / air | 1.91e−8 | 1.89e−8 | 1.44e−8 | 2.12e−8 |

FP32의 기존 baseline 대비 최대 온도 절대차는 5.158e−8 K였다. 같은 알고리즘의 IR-FP64와 직접 비교했을 때 FP32의 p/U/T/rho 최대 scaled 차이는 6.419e−10, alpha는 1.921e−8 이하였다. 모든 검사 대상 최종 내부 필드는 finite였고 p/T/rho>0이었다. 최대 phase-sum 오차는 2.878e−13, 최대 스텝별 상대 질량 수지 오차는 5.052e−8이었다.

개발용 screen은 p 차이≤1e−5, 나머지 주요 상태 차이≤1e−6, alpha 범위 [−1e−8,1+1e−8], phase-sum 오차≤1e−9, 상대 질량 수지 오차≤1e−6으로 통과했다. 이는 메인이 정한 개발용 기준이며 사용자 지정 허용치나 장시간 물리 검증이 아니다.

별도의 4스텝 audit에서 FP32 경로의 원래 온도 선형계 backward error는 최대 2.387e−17, `max|residual/diagonal|`는 3.969e−14 K였다. 이 audit는 반복 측정과 분리했다.

**raw dgdt는 동등하지 않다.** baseline 대비 최대 scaled 차이는 IPA 약 0.855, N₂O 약 0.00731, air 약 1.01까지 있었다. IR-FP64에서도 IPA 약 0.855의 차이가 나타나므로 이 현상을 FP32만의 오차라고 해석하지 않는다. raw dgdt는 일반 상태 차이 screen에서 제외한 사실을 명시한다.

첫 반복 최종장의 압축성 source 성분 `alpha_i*(Σ_j alpha_j*dgdt_j−dgdt_i)`를 별도로 계산했다. 모든 IR 설정에서 `max|dt·Δsource|≤1.877e−12`, 상대 L2≤1.193e−9였다. 이것은 순간적인 대수식 비교이며 상별 순차 수송을 재실행한 검증이나 raw dgdt의 동등성 증명이 아니다. [source 진단](precision-effective-source.json)

## 실패 경로·메모리·재현 기록

- 실제 1스텝에서 내부 `maxIter=5`, 요청 sweep=6으로 마지막 묶음이 5회로 제한되는지 확인했다. 낮은 정밀도 풀이를 중단시키고 `nSweeps=-12`인 고정횟수 FP64 fallback을 실행했다. 두 T solve 모두 fallback=1, 실제 최종 잔차 약 1.10e−16이었다. 고정횟수 stock solver의 기본 잔차값 0을 그대로 신뢰하지 않고 재검사한다.
- 같은 실행에서 `irPack`, `irStart`, `irJacobi`, `irAccumulate` FP32 커널을 Compute Sanitizer로 검사했다. 정상 종료, `ERROR SUMMARY: 0 errors`. 명시적 CUDA API 실패 검사도 포함했다. 검사 범위는 해당 FP32 커널이며 DS/TS·전체 SPUMA·race/initcheck의 통과를 뜻하지 않는다. 기존 공용 템플릿 중복 등록의 extended 진단은 [기존 기록](runtime-checks.md)과 같이 미해결이다. [검사 집계](precision-fallback-check.json) · [이번 실행 원자료](../benchmarks/precision-fallback-memcheck1/run.json)
- 최종 snapshot CLI로 새 독립 압력 시스템을 추출하고 FP64 CSR 검산을 수행했다. 원래 압력 풀이와 추출한 CSR의 일치, 전체 scalar screen, 출력 길이를 확인했다. [CLI 검산](../benchmarks/precision-snapshot-cli-check1/verify-fp64.json)
- 각 실행은 원본을 복사해 사용했다. 입력 control/fvSolution과 실행파일·로컬 라이브러리 hash는 본 배치 전후에 같았다. 사후에 초기장·mesh·관련 constant 파일을 원본과 15개 복사본 전체에서 대조했고 불일치 0건이었다. 변경한 thermo 사전도 각 실행의 설정 hash와 일치했다. [입력 무결성 대조](precision-input-integrity.json)
- source hash는 실행 후 채집한 값이며 서명된 빌드 전 manifest는 아니다. 4스텝 pilot은 반복 제한·고정횟수 fallback 재검사 보완 이전 wrapper를 사용했다. pilot에서는 해당 경로가 실행되지 않았으며, 12스텝 본 배치와 강제 fallback 검사는 보완한 wrapper의 같은 바이너리를 사용했다. 각 빌드 hash와 읽은 stdout hash를 JSON에 구분해 보존했다.

## 적용 판단

1. **이번 T 방정식에는 FP32 내부 반복 + FP64 잔차보정이 가장 유망하다.** 낮은 정밀도로 실제 내부 산술을 수행하면서 목표 잔차에 도달했다. 다만 현재 전체 성능 이득은 작아 실험 옵션으로 유지한다.
2. **2FP32는 산술량이 크고 약 14자리 정밀도로 충분한 특정 커널의 후보**다. 희소행렬의 메모리 절감 수단은 아니며 상쇄가 민감한 FP64 입력의 보존을 보장하지 않는다.
3. **현재 3FP32 구현은 정밀도 확장용에 가깝다.** FP64를 속도 목적으로 교체하기에는 이번 계산·행렬·온도 단계 측정이 불리하다.
4. 압력은 FP64 실제 잔차·보존량을 유지하고 전처리/평활화만 FP32로 바꾸는 후속 탐구가 타당하다. 직접 FP32 압력 잔차 계산은 이번 상쇄 시험을 견디지 못했다. EOS 전체의 DS/TS 포트에는 나눗셈·제곱근·초월함수와 범위 조정이 더 필요하다.

TS의 속도 결론은 구현한 일반 triple-word 알고리즘에 한정한다. FP64 수준만 목표로 특정 식의 보정 연산을 줄이는 별도 근사는 검증하지 않았다.

현재 검증은 하나의 45 μs 체크포인트, 짧은 물리 시간, 단일 GPU·비결합 경계에 한정한다. t=0 시동, 긴 이력, 다른 물성 범위, MPI, Foundation 14와의 이산화 동등성은 이 정밀도 실험으로 검증하지 않았다.
